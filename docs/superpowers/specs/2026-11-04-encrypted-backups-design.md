# تشفير النسخ الاحتياطية (Encrypted backups) — التصميم

التاريخ: 2026-11-04 · الحالة: معتمد في المحادثة، منتظر مراجعة الـ spec

## الهدف

- ملف نسخة احتياطية مسروق ما يكشفش أي بيانات (عملاء، مديونيات، password hashes، مفاتيح).
- أي ملف اتعدّل بعد ما اتعمل، ولو بايت واحد، أو اتزوّر، **يترفض** وقت الاستعادة.
- الاستعادة على **جهاز جديد** (لو جهاز السيرفر باظ) تشتغل بمفتاح استرداد مطبوع.
- مفيش باسورد يومي يفتكره المالك.

## قرارات اتاخدت

| القرار | الاختيار | السبب |
|---|---|---|
| الطريقة | مفتاح تلقائي + مفتاح استرداد مطبوع (A) | أبسط استخدام، ومفيش باسورد ضعيف يبقى نقطة دخول |
| نسيان المفتاح | مفتاح استرداد مطبوع | زي مفتاح طوارئ المدير الموجود |
| النسخ غير المشفرة (`.db`) | **تترفض دايمًا** | المشروع لسه في التطوير ومفيش نسخ قديمة عند حد |
| فتح النسخ عن طريق المطوّر | مش هيتعمل | كان هيخلّي المطوّر يقدر يفتح بيانات كل المحلات |

## خارج النطاق

- باسورد للنسخ، أو باسورد مختلف لكل نسخة.
- الحماية من حد قادر يشغّل كود من حساب الويندوز بتاع جهاز السيرفر نفسه (يقدر يستخدم المفتاح زي البرنامج).
- تشفير النسخة الطارئة اللي بتتعمل قبل الاستعادة (بتفضل `.db` في `userData` جنب قاعدة البيانات الحية).
- بند F8 (مفتاح الـ AI متخزن نص عادي) ومشكلة وقف النسخ اليومي لما الترخيص يفشل.

## 1. شكل الملف `.fbk`

```
offset  size  field
0       4     magic  "FXBK"
4       1     format version = 1
5       8     keyId  = first 8 bytes of SHA-256("fxbk-key-id" || key)
13      12    nonce  (random per file)
25      n     ciphertext  (AES-256-GCM of the SQLite file bytes)
25+n    16    GCM auth tag
```

- **AAD** = أول 25 بايت (magic + version + keyId + nonce). أي تعديل في الهيدر أو المحتوى يفشّل الـ tag.
- المحتوى بيتعمل من `db.backup()` في ملف مؤقت جوه `userData/backups/.tmp`، يتقري، يتشفّر، يتكتب ذرّيًا (temp + rename)، والملف المؤقت غير المشفّر يتمسح في `finally`.
- الملف بالكامل بيتحمّل في الذاكرة (قواعد بيانات المحلات بحجم ميجابايتات). البث (streaming) مش مطلوب دلوقتي.

## 2. المفتاح وحلقة المفاتيح (keyring)

- **المفتاح:** 32 بايت عشوائي (`crypto.randomBytes`).
- **التخزين:** ملف `userData/backup.key` (JSON):
  ```json
  { "version": 1, "primary": "<keyId hex>", "keys": { "<keyId hex>": "<safeStorage-encrypted base64>" } }
  ```
  كل مفتاح متشفّر بـ `safeStorage.encryptString` (DPAPI على ويندوز). الملف **برّه قاعدة البيانات** فما يدخلش في أي نسخة.
- **لو `safeStorage.isEncryptionAvailable()` بـ false:** إنشاء أو قراءة المفتاح يرمي خطأ واضح. مفيش fallback لمفتاح مكشوف.
- **إنشاء المفتاح:** `ensureBackupKey()` بتعمله لو مش موجود. بتتنده في إنشاء حساب المدير الأول، وأول ما أي نسخة تحتاجه.
- **التشفير** دايمًا بالمفتاح `primary`. **فك التشفير** بأي مفتاح في الـ keyring يطابق `keyId` بتاع الملف.

## 3. مفتاح الاسترداد

- **الشكل:** `FXR-` ثم 32 بايت المفتاح + 2 بايت checksum (أول 2 بايت من SHA-256 للمفتاح)، متكتبين Base32 (RFC 4648 بدون padding) في مجموعات من 4 حروف مفصولة بـ `-`.
- **التحليل:** متسامح مع المسافات والحروف الصغيرة والشرطات. لو الـ checksum غلط يرجع خطأ "في غلطة في كتابة المفتاح".
- **الاعتماد (adopt):** لما يتدخل مفتاح استرداد صحيح بيطابق `keyId` ملف بيتسترجع، المفتاح بيتضاف للـ keyring ويبقى `primary`، والمفاتيح القديمة بتفضل للقراءة بس.

## 4. الوحدات (units)

| الملف | المسؤولية |
|---|---|
| `electron/security/backupCrypto.js` (جديد) | دوال نقية: `encryptBackup(buf, key)` و`decryptBackup(buf, keyring)` و`readHeader(buf)` و`formatRecoveryKey(key)` و`parseRecoveryKey(text)` و`keyIdOf(key)`. مالهاش اعتماد على Electron |
| `electron/services/backupKey.service.js` (جديد) | الـ keyring على الديسك مع `safeStorage`: `ensureBackupKey()` و`getPrimaryKey()` و`getKeyring()` و`adoptRecoveryKey(text)` و`getRecoveryKey()` |
| `electron/services/backup.service.js` | `backupToFile` بيكتب `.fbk`. `restoreDatabase(path, { recoveryKey })` بيفك التشفير لملف مؤقت جوه `userData` وبعدين يكمّل بالفحوص الموجودة. تعديل الـ pruning لامتداد `.fbk`، و`getDefaultBackupPath` بقى `.fbk` |
| `electron/handlers/backup.handler.js` و`settings.handler.js` | فلتر الـ dialogs على `.fbk`. الـ restore بيرجع `{ needsRecoveryKey: true }` لما الملف لمفتاح غير معروف. قناة `backup:getRecoveryKey` بتاخد `{ password }`، وبتشترط المدير الرئيسي وكلمة مروره |
| `electron/handlers/auth.handler.js` | `auth:createInitialAdmin` بيرجع كمان `backupRecoveryKey` |
| `electron/preload.js` | تمرير الوسائط الجديدة: `restoreDatabase({ recoveryKey })` و`getBackupRecoveryKey(password)` |
| `src/pages/InitialSetupPage.jsx` | عرض مفتاح استرداد النسخ جنب مفتاح طوارئ المدير، مع نسخ وطباعة |
| `src/pages/SettingsPage.jsx` | حالة "النسخ مشفّرة"، وزرار "عرض مفتاح استرداد النسخ" (بيطلب الباسورد)، وخانة إدخال مفتاح الاسترداد وقت الاستعادة |

## 5. مسار الاستعادة

1. `readHeader`: لو الـ magic أو الإصدار غلط → **رفض**: "الملف ده مش نسخة احتياطية مشفّرة من البرنامج".
2. البحث عن `keyId` في الـ keyring. لو مش موجود ومفيش `recoveryKey` → يرجع `{ needsRecoveryKey: true }` من غير ما يلمس حاجة.
3. لو فيه `recoveryKey`: `parseRecoveryKey`، ولازم `keyIdOf(key) === header.keyId` وإلا "المفتاح ده مش بتاع النسخة دي". بعدين فك التشفير.
4. فك التشفير: لو الـ GCM فشل → **رفض**: "الملف اتعدّل أو تالف ومش هيتسترجع".
5. كتابة الناتج لملف مؤقت جوه `userData`، وبعدها الخطوات الموجودة: `verifyDatabase`، و`sanitizeRestoreCandidate`، والنسخة الطارئة، والاستبدال الذرّي، و`rotateSecret`، وإعادة التشغيل.
6. `adoptRecoveryKey` بيتنفذ **بعد ما فك التشفير ينجح وقبل الاستبدال**، فمفتاح غلط عمره ما يدخل الـ keyring.
7. الملف المؤقت غير المشفّر بيتمسح في كل الحالات.

## 6. الأخطاء

| الحالة | السلوك |
|---|---|
| ملف مش `.fbk` أو هيدر غلط | رفض، والقاعدة الحية ما تتلمسش |
| tag غلط (ملف متعدّل) | رفض، والقاعدة الحية ما تتلمسش |
| مفتاح استرداد فيه غلطة كتابة | خطأ checksum قبل أي فك تشفير |
| مفتاح استرداد صحيح بس لنسخة تانية | رفض، والـ keyring ما يتغيّرش |
| `safeStorage` مش متاح | النسخ يفشل والخطأ يتسجّل ويظهر في الإعدادات |
| فشل أثناء النسخ | مفيش ملف `.fbk` ناقص، والملف المؤقت يتمسح |

## 7. الاختبارات (تتكتب قبل الكود)

- `backupCrypto`:
  - تشفير وفك تشفير يرجّع نفس البايتات.
  - قلب أي بايت (في الهيدر أو المحتوى أو الـ tag) يفشّل الفك.
  - مفتاح غلط يفشل.
  - ملف SQLite عادي يترفض.
  - `formatRecoveryKey` و`parseRecoveryKey` بيرجّعوا نفس المفتاح، ومتسامحين مع المسافات والحروف الصغيرة، وبيمسكوا غلطة حرف واحد.
- `backupKey.service` (مع `safeStorage` mock بيشفّر بشكل قابل للعكس):
  - المفتاح بيتعمل مرة واحدة ويثبت بعد إعادة التشغيل.
  - الملف مش فيه المفتاح نص عادي.
  - لو `safeStorage` مش متاح يرمي خطأ.
  - `adoptRecoveryKey` بيخلّي المفتاح الجديد `primary` ويحتفظ بالقديم.
- `backup.service`:
  - `backupNow` والنسخ اليومي ونسخ الإغلاق بيطلّعوا `.fbk` يبدأ بـ `FXBK`.
  - مفيش ملف غير مشفّر بيفضل في مجلد الوجهة أو `.tmp`.
  - الـ pruning بيشتغل على `.fbk`.
- الاستعادة:
  - نفس الجهاز بتشتغل.
  - ملف متعدّل بايت واحد يترفض والقاعدة الحية زي ما هي.
  - ملف `.db` يترفض.
  - "جهاز جديد" (keyring فاضي غير مفتاح تاني) بيرجع `needsRecoveryKey`، وبعدين بالمفتاح الصح بتنجح والمفتاح يتعتمد، وبالمفتاح الغلط ترفض والـ keyring ما يتغيّرش.
- الـ handlers:
  - `backup:getRecoveryKey` بيرفض من غير باسورد المدير الصح، وبيرفض أي دور غير المدير الرئيسي.
- الـ IPC coverage test الموجود لازم يفضل أخضر مع القناة الجديدة.

## 8. ملاحظات التوافق

- نسخ `.db` القديمة الموجودة في `userData/backups` على جهاز المطوّر ما بتتلمسش ولا بتتقبل في الاستعادة.
- مفيش migration لقاعدة البيانات. كل حاجة جديدة برّه قاعدة البيانات.
